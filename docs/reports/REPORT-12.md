## 1. 你给的这行诊断是决定性的

```
textarea:textarea.xterm-helper-textarea 10×19 | term:div.terminal.xterm 912×591
0 个 iframe · 回包 1 · 可写 0
```

三个结论一次到位：

1. **编辑器不是文本编辑器，是终端**（`div.terminal.xterm` 912×591）；
2. 页面上唯一的 textarea 是 **xterm 的辅助输入框**，只有 10×19 —— 它是给键盘事件用的，不是给"往 value 里灌代码"用的；
3. `可写 0` 说明上一轮的可见性闸门**正确地把它挡掉了**——如果没挡，我们会往这个 10×19 的框里写 19 行 SQL，"写入成功"、页面毫无反应、评测还是 0/1。你看到的现象和这条推断完全对上。

所以你之前那句"代码人工验证是对的"没错，问题从头到尾都是：**代码从没进过终端**。

## 2. 修复：terminal 适配器

| 环节 | 做法 |
|---|---|
| 识别 | `deepQuery('.xterm, .xterm-screen, [class*="terminal"], [class*="console"]')` → `kind: 'terminal'` |
| 读取 | 读 `.xterm-rows` 的可见文本（屏幕内容），不读 textarea |
| 写入 | 常规写入直接跳过（终端没有"文档"可写），交给受信任输入 |
| 执行 | CDP `Input.insertText` 键入后补一次 `Enter`（keyDown + keyUp），等价于人工敲完回车 |
| 校验 | 按行命中率判断：代码里 ≥60% 的行出现在终端屏幕上即算写入成功（容忍折行和提示符） |

`focusEditor()` 也改了：终端分支优先，把焦点交给 xterm 的辅助 textarea —— xterm 就是靠它接收键盘。

状态行会明确写：

```
已写入 19 行（受信任输入 · terminal · 已回车执行）
```

## 3. 为什么之前"点了评测也成功"

评测按钮在页面里，点击一直没问题；问题在于评测读取的是**终端里执行过的 SQL**。终端里空着，评测自然是 0/1 组不匹配。这也解释了为什么答案本身对、结果却错。

## 6. 风险备注

- 受信任输入每次会短暂 attach 调试器（顶部提示条），终端任务必须走这条路，没有替代方案；
- 回车后若终端立即回显且自动执行，可能出现"先执行、再被我们点击评测"的时序，正常；
- 行命中率判定容忍折行，但若终端把 SQL 全部折成一屏外的滚动区，命中率会低于阈值 → 报 `INJECT_MISMATCH`，此时应以"终端里有内容"为准，下一轮放宽。
