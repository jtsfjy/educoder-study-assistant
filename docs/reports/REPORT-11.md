## 1. 关键判断：已连接 ≠ 连对

`requestEditor` 只要求"某一帧回了一个 kind≠none 的编辑器"，从不校验**那个元素是不是真的在屏幕上**。而这类页面里最容易被误认成编辑器的是：

| 元素 | 典型特征 | 后果 |
|---|---|---|
| `textarea.xterm-helper-textarea` | 1×1 或 0×0，透明，用于接收键盘 | 写 `value` 成功，终端毫无反应 |
| 隐藏的同步 textarea | `position:absolute; left:-9999px` | 同上 |
| 页面底部/顶部的搜索框 | 面积正常 | 代码写进搜索框 |

**"已连接但注入无反应、评测跑的还是旧内容"——这三件事完全吻合第一种情况。** 写入成功、回读一致，但平台读取的编辑器状态没变。

## 2. 修复

### 2.1 可见性闸门

新增 `isPlausibleControl()`：宽 ≥ 80px、高 ≥ 18px、在视口坐标系里有占位（`bottom > 0 && right > 0`）、`display/visibility` 正常。

- `readEditor()` 对 textarea / contenteditable 先过这道闸门，不合格就报 `none`，**不再把隐藏输入框当编辑器**；
- `writeEditor()` 同样只往合格控件里写。

### 2.2 候选摘要（这轮的重点）

诊断区新增一行**「候选」**，把页面上所有可能是编辑器的元素摊开：

```
textarea:textarea.xterm-helper-textarea 1×1 | editable:div.cm-content 720×480 | term:div.xterm 720×480
```

- 有 `1×1`、`0×0`、类名带 `xterm` / `helper` → 目标选错了，下一步按终端处理；
- 有正常尺寸的 `editable:` 但注入仍无效 → 是"框架不认合成事件"，上一轮的受信任输入应该生效；
- 全都没有 → 编辑器可能是 canvas 自绘，需要换注入方式。

写入失败的报错里也会附上这段候选摘要，不用再靠猜。

## 3. 为什么"给诊断行"比"给 JS 文件"有用

一段 JS 只能证明"跑到这个文件"，而诊断行直接说明**页面上到底有哪几个可写目标、各自的真实尺寸**。一行的信息量比一万行打包代码大。

## 6. 风险备注

- 闸门可能误杀"滚动到视口外的大编辑器"（`bottom <= 0` 时判定不可用）。真遇到时报 `none`，我会放宽为"祖先容器可见"判断；
- 候选摘要是只读的，不写入、不点击；
- 隐藏输入框不再被当作编辑器，若某些平台真的把代码存在隐藏 textarea 里，会表现为"未连接"而不是"注入无效"——这比静默失败好判断。
